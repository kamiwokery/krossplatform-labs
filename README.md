## Как посмотреть историю

```
git log --graph --oneline --all
```

На графике видны ветки `lr1`…`lr14` и merge-коммиты слияния в `master`.

## Как повторить работу (порядок выполнения)

Для каждой лабораторной работы (пример — ЛР2):

```bash
# 1. Ветка от актуального состояния master
git checkout master
git pull                      # при работе с удалённым репозиторием
git checkout -b lr2

# 2. Добавить файлы работы
# ... скопировать файлы ЛР2 ...
git add .
git commit -m "ЛР2: задания варианта 15 (массивы)"

# 3. Слить в master обычным merge (создаётся merge-коммит)
git checkout master
git merge --no-ff lr2 -m "Merge branch 'lr2' (ЛР2)"

# 4. Перед следующей работой — новая ветка от актуального master
git checkout -b lr3
```

## Публикация на GitHub

```bash
git remote add origin https://github.com/kamiwokery/krossplatform-labs.git
git push -u origin master
git push origin lr1 lr2 lr3 lr4 lr5 lr6 lr7 lr8 lr9 lr10 lr11 lr12 lr13 lr14
```

Затем на github.com: `New pull request` → ветка `lrN` → `base: master` → `Create pull request` → `Merge pull request` → **Create a merge commit** (не squash/rebase!) — так создаётся отдельный коммит слияния, как требуется по заданию.

## Ответы на контрольные вопросы

1. **Что такое система контроля версий и зачем она нужна?** VCS — система, записывающая изменения в файлы со временем и позволяющая вернуться к любой версии. Нужна для отката ошибок, просмотра истории и кто что менял, совместной работы, резервного копирования истории проекта.

2. **Чем отличается Git от других VCS (SVN, Perforce)?** Git — распределённый (DVCS): каждый клиент хранит полную копию репозитория с историей, работает офлайн, сервер — не единственная точка отказа. SVN/CVS — централизованные: единый сервер, без сети не сохранить. Кроме того, Git хранит снимки (snapshots) всего проекта, а не список дельт, почти все операции локальные, целостность через контрольные суммы SHA-1.

3. **Три состояния файла в Git:** `Modified` (изменён, не зафиксирован), `Staged` (подготовлен к следующему коммиту через `git add`), `Committed` (безопасно сохранён в локальную базу). Им соответствуют рабочая директория, индекс (staging area) и репозиторий.

4. **Основные команды Git:** `git init`, `git clone <url>`, `git status`, `git add <файл>`, `git commit -m "..."`, `git log`, `git diff`, `git branch`, `git checkout`, `git merge`, `git pull`, `git push`, `git revert`, `git reset`.

5. **Ветка в Git и зачем она нужна:** независимая линия разработки. Позволяет работать над новой функциональностью, не затрагивая стабильный код, экспериментировать без риска, вести параллельную разработку. Создание: `git branch <имя>`, `git checkout -b <имя>` — создать и переключиться.

6. **Конфликт слияния и его разрешение:** возникает, когда две ветки изменили одну и ту же часть файла по-разному. Git помечает участки маркерами `<<<<<<<`, `=======`, `>>>>>>>`; разработчик вручную выбирает правильный вариант в редакторе, затем `git add` и `git commit`.

7. **GitHub и отличие от Git:** Git — локальная система контроля версий (инструмент), GitHub — облачная платформа для хранения Git-репозиториев и совместной работы: форки, Pull Request, код-ревью, issue-трекер, CI.

8. **Pull Request и зачем он нужен:** механизм предложить изменения в репозиторий (форк/ветка → push → PR → ревью → merge). Нужен, чтобы код проходил обсуждение и ревью перед слиянием, сохранялась история обсуждений.

9. **Файл .gitignore и зачем он нужен:** перечисляет файлы, которые Git не отслеживает: скомпилированные `*.class`/`*.jar`, `target/`, настройки IDE (`.idea/`, `*.iml`), файлы ОС, пароли и ключи — чтобы они не попадали в открытый репозиторий.
